# 故障统计性能诊断分析（2026-09-17）

数据来源：`statistics-performance-1789623977542.json`，导出时间北京时间 2026-09-17 13:46:17。

## 结论

主要问题是汇总接口重复构建多个页面所需的数据、无条件加载三套明细，以及后端历史记录加载和重复故障计算。常见慢请求中 SQL 执行耗时只占较小部分，不能简单归结为数据库查询慢或缺少索引。另有一次明显的视图外等待异常，需要单独检查。

本次只分析数据和对照源代码，未修改统计逻辑或服务器配置。

## 样本与限制

- 共 45 个请求，均返回 HTTP 200：10 个故障汇总、32 个故障明细、1 个业务汇总、2 个业务明细。
- 291 条同步渲染记录、40 条长任务、17 条交互标记；总计 945 次 SQL、约 13.62 MiB 原始响应体。这是跨多次操作的累计值，不是一次打开页面的开销。
- 记录含长时间停留，不能用导出时刻减页面加载时刻作为加载耗时。
- 四次同参数的“2026 年、不筛省份”汇总可用于观察稳定范围，但不足以估计可靠的生产 P95；大多数其他场景仅一个样本。
- 未采集 2026 年命中缓存的对照样本；2025 年数据很少，不能将其速度直接类推到 2026 年。
- 后端阶段 `ms` 含子调用，不能相加；`self_ms` 不含已计时子调用，但仍含未细分代码、SQL、对象处理、序列化及进程调度时间，不等于纯 CPU。

## 按收益优先级排查

### 1. 汇总接口承担了多个页面的工作

四次 2026 年全省汇总的后端阶段：

| 阶段 | 单次耗时范围 | 含义 |
|---|---:|---|
| 当前期子公司统计 | 2.67～3.25 秒 | 包含下面的绩效，不可再次相加 |
| 子公司绩效（子公司阶段内） | 1.17～1.73 秒 | 包括年度裸纤与历史重复数据加载 |
| 当前期主管统计 | 1.27～1.30 秒 | 与当前选中的物理省份无关 |
| 汇总视图自身未细分部分 | 2.12～2.29 秒 | 需要继续拆分物理查询、对象处理和序列化 |
| 两次上一年对比计算合计 | 0.33～0.37 秒 | 年统计的环比和同比区间完全相同，重复执行 |

子公司和主管阶段合计约占全省汇总 56%（以各阶段中位数与视图中位数估算）。筛上海时，两者仍耗时 **4.59 秒，占视图 74.8%**；筛上海+北京时约 4.64 秒，占 74.6%。这解释了为什么单省明细已经很少，筛省份仍要等数秒。

建议先拆分物理周期统计、主管统计、子公司统计和年度绩效的加载/缓存范围；省份改变只刷新相关物理数据。年度趋势与绩效按年份和口径复用。年统计中同起止时间的环比/同比只算一次。此处 4.59 秒是现有阶段开销，不是对优化后绝对节省量的保证。

证据示例：`253a33e553a1419e`（上海汇总），`8b1ba2e03aaf4503`（全年汇总）。

### 2. 每次操作都重新加载三套完整明细

10 次故障汇总之后均有物理、子公司、主管三套明细请求，另有 2 次独立下钻。32 个明细请求占全部请求的 71%。

2026 年常规返回行数为物理 1148、子公司 241、主管 907。三套明细存在重叠：子公司与主管基本对物理范围进行分区，因此将其全部加载会重复读取和处理同一批故障。

筛上海后，物理明细只有 26 条，但仍请求全范围的 241 条子公司和 907 条主管明细。切主管页还会重新取物理明细。源码 `loadData()` 中三次无条件明细加载与实测一致。

建议只加载当前可见 Tab 的明细，必要时在下钻时加载；日期及范围未变化时复用数据。旧响应不应覆盖新选择，并通过取消请求/版本号防止快速切换造成无效渲染。需注意取消浏览器请求不一定终止已经运行的后端计算。

### 3. 后端重复检测和历史对象加载比前端排序更值得优化

| 范围 | 返回行数 | 后端 detect_repeat_faults |
|---|---:|---:|
| 物理全年未筛选（3 次） | 1148 | 1.929～1.937 秒 |
| 主管全年（8 次） | 907 | 1.127～1.155 秒 |
| 子公司全年（8 次） | 241 | 0.104～0.107 秒 |

这些阶段 SQL 次数均为 0，说明该阶段主要是已加载对象的处理和匹配，而非执行 SQL。三套明细反复进行历史加载和重复检测，放大总成本。

查询执行次数少也不代表加载便宜：例如明细的 `load_current_faults` / `load_preceding_faults` 阶段，包含结果抓取、关联装配和模型实例化。应减少不需要的字段和历史候选，复用站点集合/时间窗口及重复关系；按样本量测试算法增长。不能仅凭这些计时断言具体哪个模型字段最慢。

相比之下，前端 `sortDetailRows` 最大仅 **3.8 ms**，`assignRepeatGroupColors` 最大 **40.2 ms**。本次不应优先重写前端排序。

### 4. 当前周期每次重算；缓存策略需要按模块调整

8 次 2026 年故障汇总全部为 `live_period_uncached`。切 Tab 或省份不能受益于已有的长缓存。2025 年相同参数汇总从 miss 的后端 782.58 ms 降至 hit 的 34.20 ms，说明缓存机制可用。

建议采用短 TTL 或数据变更失效机制，并将不随物理省份改变的统计独立缓存；同页 Tab 切换保留参数一致的数据。不要因为“当前周期”就把所有昂贵历史/年度数据一并视为不可缓存。

### 5. 一个约 10 秒的视图外等待需要独立调查

主管明细 `bee0d113d3524390`：

- 浏览器总耗时 12854.30 ms；等待响应头 12811.00 ms。
- 后端视图 2868.91 ms，SQL 161.31 ms。
- 两者差额 **9985.39 ms**。

这部分不在当前后端计时范围内，可能是浏览器/连接排队、代理或 worker 排队、请求中间件、网络、进程调度等，不能称为“SQL 慢 10 秒”。应针对对应时间采集 Nginx request_time/upstream_response_time、Gunicorn 并发/繁忙 worker、系统 CPU/内存及浏览器 Network Timing。当前 JSON 无法确认具体根因。

### 6. 前端有卡顿，但不是稳定 8 秒等待的主因

- 首次 `renderBranchCompanySection` 434.2 ms，其中绩效卡片 222.9 ms；两者有包含关系。
- `renderLineSupervisorSection` 最大 124.4 ms。
- 业务卡片约 286.0 ms；物理明细最大 177.4 ms。
- 40 条页面级长任务，最长 529 ms，可能包括浏览器布局和其他脚本，不能全部归因于某个图表。
- 响应体读取+JSON 解析中位数 28.8 ms、最大 108.6 ms，最大单个原始响应不足 1 MiB。此次不支持“JSON 解析是首要瓶颈”的结论。

建议延迟构建隐藏页面图表和绩效/月历，复用 ECharts 实例，减少重复 setOption 和 DOM 更新；在减少后端工作与请求后再进一步优化。

业务汇总另有具体线索：`load_yearly_impacts` 973.01 ms，但 SQL 执行仅 32.22 ms；当前、年度、月历加载合计约 1599 ms，占业务视图约 92.7%。应检查三份业务影响数据的重复加载和实例化，而不是先优化耗时仅几十毫秒的统计循环。

## 诊断机制本身发现的问题

1. Tab 的一次点击被记为相邻的 `tab:*` 与 `click:*` 两个 action_id：汇总和明细可能分属不同 action，不能机械按 action_id 汇总整次交互。本报告按时间邻近和接口批次辅助核对。
2. 原因图表下钻未产生新的交互记录：有一个耗时 616.7 ms 的请求被归到约 580 秒前的 Tab 点击。`action_elapsed_ms` 在这里包含用户停留时间，不能当作操作耗时。
3. 首次汇总参数是 week=38，紧随的三套明细参数却是 year=2026。该参数不一致已确认；是否由默认控件同步、异步状态变化或漏记的操作引起尚待复现。应让一批请求使用同一份筛选快照。
4. 自动阈值没有提示最主要的 8 秒汇总，因为 96 条 SQL 未达到 100，SQL 耗时占比也低；相反两个仅几十毫秒的请求因 SQL 占比高而被提示。应增加绝对耗时阈值、跨交互同参数重算提示，并用最小绝对耗时约束 SQL 占比告警。
5. 只有单次极慢视图外差额样本，不能将 12.85 秒称为稳定 P95。需按固定数据与固定操作补充至少 20 次样本。

## 推荐实施顺序及验收

1. 先补齐交互归因和筛选快照，避免错配参数和误判耗时；复现周汇总/年明细问题。
2. 按当前 Tab 加载明细和图表，保留同参数页面数据；验收切物理省份不发主管/子公司明细请求。
3. 拆分/复用主管、子公司、年度绩效，去重相同对比区间；验收筛省份不重复执行无关分组阶段。
4. 优化重复检测与查询集装配；用相同 1148/907/241 条数据对照耗时，并验证重复故障集合、KPI、历史记录不变。
5. 根据视图外差额的第二轮证据处理 worker/代理/网络；不直接盲增 worker 或数据库索引。

每轮分别记录汇总就绪时间、当前页明细就绪时间、请求数、SQL、阶段耗时以及数据库外差额。2026 年当前周期、2025 年已结束周期分开测试；优化前后必须采用相同诊断开关和统计口径。
